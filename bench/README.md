# DriftBench

A seeded set of container pairs with a known injected cause, used to score diagnosis quality (top-1, top-3, MRR, false-CONFIRMED rate, Brier). Each scenario is a green arm and a red arm that run one small program. The red arm fails at a declared rate and the green arm passes.

The benchmark is synthetic. The cause is ground truth because the scenario was built around it, not because it was observed in the wild. Scenarios whose cause a container cannot vary (kernel, CPU model, browser) run one configuration in both arms, and the capsule values for the cause are written in. They are marked `controllable: false` and `expected.manual: true`.

## Layout

- `scenarios/*.yml`: hand-maintained templates, one file per dimension.
- `data/scenarios.json`: generated scenarios, one per line. `data/split.json`: dev and test ids and the sha256 of the sealed test list.
- `data/results/<id>.json`, `data/capsules/<id>.<arm>.json`: measured output for dev scenarios. `data/dropped.json`: scenarios that failed validation, with their counts.
- `data/probed/<id>.green.json` and `.red.json`: the passing and failing baseline captures of `drift solve`, with probes. `data/calibration/`: `fit.json` and `evaluation.json`, generated by `calibrate`. `data/freeze.json` and `data/unseal.log`: the frozen hashes and the log of the one unseal (see Split).
- `runner/harness.sh` runs inside each container. `runner/run-batch.sh` runs prepared scenarios on any docker host. `runner/native.sh`, `harness.ps1` and `native.ps1` run them on the host without Docker (see Host Arms).

## Template Fields

A template file has `schema: 1` and a `templates` list. Every scalar is a string.

- `id`, `instances`: scenario ids are `<id>-1` to `<id>-N`.
- `variants`: rows of placeholder values; a seeded shuffle picks `instances` rows. `draw`: lists of values drawn independently per instance. `{{name}}` is replaced in values and in map keys.
- `dimension`: one of the 14 dimensions. `runtime`: `sh`, `python3`, `node`, `java`, `go`, `ruby`, `php`, `dotnet` (an F# script), `rust`, `r`, `dart`, `julia` or `elixir`. `program`: the source.
- `signature` (text in the output) or `exit` (exit code) that every failing trial must show.
- `gate`: permille of trials where the fault is armed (default 1000). `trials` (default 20).
- `base`, `green`, `red`: run configuration (`image`, `env`, `memory`, `cpus`, `cpuset`, `ulimits`, `network`, `files`, `interpreter`, `args`, `gate`, `rate`). `base` is merged under each arm. Defaults: 512m, 2 CPUs, `--network none`.
- `cause`: `none` or `dimension`, `path` (the capsule path), `attribute`, `direction`. `bundle` and `decoys`: lists of `dimension` and `path`; a blank path is skipped. `visible: false` marks a cause the capsule cannot see.
- `controllable: false` with `capsule-overrides` (`path`, `green`, `red`) for causes a container cannot vary.

The class of a scenario is derived: `control` (no cause), `intermittent` (red rate under 1000), `bundle`, `decoy`, else `single`.

## Trial Outcomes

The harness arms the fault on trial `i` when a fixed integer hash of `i` and the scenario salt is under the gate (`Gate.kt` and `harness.sh` compute the same function), so the failing trials are known before docker runs. The program fails only when the fault is armed and the injected cause is present in its environment. A scenario is valid when both arms finish, the green arm passes, every red failure carries the signature, the failing trials equal the prediction, and the red failure count is within an exact two-sided binomial tolerance (each tail at least 0.0005) of the declared rate. A scenario that fails is listed in `data/dropped.json` with its counts and left out of `scenarios.json`.

## Commands

Run from the repository root. `--root` is the absolute path of this directory.

- `./gradlew :bench:jvmRun --args="generate --root <bench>"` writes `data/scenarios.json` and `data/split.json` (the seed is `Work.SEED`).
- `... --args="prepare --root <bench> --out <dir> [--only a,b] [--template t,u]"` writes one directory per dev scenario. A test id is refused. `--test` writes the test scenarios instead and works only after the unseal.
- `DRIFT=<linux drift binary> sh <dir>/run-batch.sh <dir>` runs both arms of every prepared scenario in docker and writes `<arm>.out`. It stops below 25 GB free.
- An arm whose image name contains `alpine` runs on a derived image (`drift-bench-gcompat:<image>`) built with `apk add gcompat libgcc`, because the Linux `drift` executable links glibc and captures nothing on a bare musl image (`libgcc` is missing from the `alpine` and `python` images). Alpine releases before 3.20 fail either way: their `gcompat` has no `libresolv.so.2`. Building it needs network access, which the arm itself does not have.
- To solve an intermittent scenario, pass its gate to `drift solve` and leave `BENCH_FLAKE` out of `--run`: `--gate permille=<red gate>,salt=<scenario salt>,env=BENCH_FLAKE` arms the same trials as the harness, so the red arm fails at the declared rate and not on every trial.
- `prepare` also writes `solve.sh` into each scenario directory that has committed capsules, with `capsule.green.json`, `capsule.red.json`, `workspace/` (the program) and `images` (the arm image tags, one per line). `DRIFT=<linux drift binary> sh <dir>/solve.sh` runs `drift solve` with every argument taken from the scenario: the failing command is `BENCH_FLAKE=1 <runtime> <file>` (an intermittent scenario passes `--gate` instead and leaves `BENCH_FLAKE` out), `--fail-when` is the signature (or `exit`), and the case goes to `$SOLVED/<id>` (default `<dir>/../solved`). It points `DOCKER_CONFIG` at an empty directory under `$TMPDIR`, writes `solve.out`, `solve.err` and `solve.verdict`, and kills the solve after `SOLVE_TIMEOUT` seconds (default 2700), recording `timeout`.
- `DRIFT=<binary> sh <dir>/run-solve.sh <dir> [--jobs N] [id...]` solves the prepared scenarios one at a time (`--jobs` runs N at once), appends `id verdict seconds` to `<dir>/solve.log` and skips an id that has a `solve.verdict` or a case. It stops below 25 GB free. It never pulls: a scenario whose arm image is missing is logged as `no-image` and runs on a later call. Counterfactual images that the solve itself needs are not checked.
- `sh <dir>/prepull.sh <dir>` prints the distinct arm image tags of the prepared scenarios. With `--pull` it pulls the missing ones one at a time, smallest first by `<dir>/image-sizes.txt` (`tag bytes` lines, unknown sizes last), and stops below 25 GB free.
- `... --args="ingest --root <bench> --prepared <dir> --drift <binary>"` validates the output and writes results, capsules and `dropped.json`.
- `... --args="probed --root <bench> --solved <dir>"` copies the passing and failing baseline captures (`arms/p0-control`, `arms/p0-treatment`, probes included) of each `drift solve` case directory to `data/probed/`. A test id is refused. A case that lacks either capture is skipped with one line (`skipped <id>: no capsule for <arm>`), nothing is written for it, and the command ends with `skipped <n>`; `--strict` exits 1 when any case is skipped.
- `... --args="freeze --root <bench>"` writes `data/freeze.json`. `... --args="unseal --root <bench>"` checks it and logs the unseal; `--dry-run` checks without logging.
- `... --args="upgrade --root <bench>"` writes `upgrade/upgrade.json` and prints the dev upgrade-check scores (see Upgrade Check).
- `... --args="calibrate --root <bench>"` runs the ranker on the probed pairs and the original capsules and writes `data/calibration/fit.json` and `evaluation.json`.

## Host Arms

A host arm runs a prepared scenario directly on the machine, with no container, so the host's own userland, filesystem and operating system are what the program sees. Host arms exist for macOS, Windows and arm64 Linux, which the local Docker hosts cannot reproduce.

`prepare` writes `<arm>.env` (the arm's variables as `export` lines) next to each `<arm>.plan`. `runner/native.sh <prepared>` runs every scenario directory with `sh harness.sh <arm>` in its own process and writes `<arm>.out` in the layout `ingest` reads. `runner/native.ps1 -Root <prepared>` does the same with `runner/harness.ps1` and needs PowerShell 7 and `sh` on `PATH` (Git for Windows provides it). Set `DRIFT_BIN` to an absolute path of the `drift` executable of the host to record the capsule of each arm.

A native run applies the arm's environment variables, arguments and interpreter. The image is ignored and the program uses the host's tools. A scenario whose arms set files, ulimits, a cpuset, memory, CPU or network settings other than the defaults cannot run without a container: `prepare` writes `native.skip` with the reason and both native scripts skip it.

All three harnesses compute the same trial gate. `harness.sh --hash` and `harness.ps1 -Hash` read `<trial> <salt>` lines from standard input and print `Gate.hash`; `RunnerTest` compares both with the engine on 1,000 inputs, and runs the PowerShell side when `pwsh` is on `PATH`.

`.github/workflows/bench.yml` runs host arms on `macos-15`, `windows-2025` and `ubuntu-24.04-arm`, one job per host. Its inputs are `ids` (scenario ids), `template` (a template id, every instance) and `hosts` (runner labels). Each job uploads the prepared directory with its outputs as `bench-<name>`. Host scenarios are observed only: there is no `solve` on a host arm, because `solve` needs Docker experiments.

`ingest` writes `data/results` and `data/capsules` by scenario id, so ingest the output of one host at a time into a scratch copy of this directory (`--root <copy>`) to keep the Docker results of the same id.

## Split

A scenario is in dev when the first four bytes of `sha256(id)`, read as an unsigned integer, mod 100 are under 60. The other scenarios are the test set. A template written after the first 43 is held out when its own id fails the same test: it has test instances only. The 43 original templates keep the instance-level split (`SplitRule.LEGACY_TEMPLATES`), so each has a dev instance. A template whose id is in the dev bucket splits per instance. A template has at most three instances, and the analysis clusters by template, so the sample size is the template count.

Test scenarios fall into three strata: dev (the scenario is in dev), test-sibling (a test scenario whose template has dev instances) and test-novel (a test scenario of a held-out template, which never ran). `holdout_templates` in `data/freeze.json` lists the test-novel templates.

Template authors do not read `rules/`, and rule authors do not read `scenarios/`. This is a rule for the people and agents who write them; nothing in the build enforces it.

### Freeze and Unseal

`freeze` writes `data/freeze.json` from the working tree: the commit, the SHA-256 of the rule catalog that `embedRules` produces, of `fit.json`, `evaluation.json`, `scenarios.json` and `split.json`, and the held-out template list. It refuses if the ranker no longer reproduces the two calibration files.

`unseal` is the only way to the test set. It runs when every value in `freeze.json` matches the working tree and the ranker still reproduces the calibration files. On a mismatch it exits 1 and names each field with the frozen and the current value. On success it appends `timestamp`, `commit` and `operator` to `data/unseal.log` and prints the number of test scenarios. The log takes one entry: a second `unseal` or `freeze` refuses. `prepare --test` and a `Lab` built with the unsealed ids check the freeze again, so a change after the unseal blocks the test run.

The check covers the rules, the scenario list, the split and the ranker output on the dev pairs. It does not hash engine source: an engine change that leaves the dev ranking and both calibration files identical passes, and the commit in the log is the record of what ran.

The test set is run once, at the frozen commit, and the result is reported whatever it is, including a null result. A fix that lands afterwards is reported next to it and does not replace it. The test results are written under `data/` and are not read by `calibrate`.

## Triage

`triage/` is a second category, scored on its own and never pooled with the scenarios above. `triage/items.yml` lists the items by hand: an `id`, a `source` and a `body`, and a `correction` where an item has a labelled claim. A `fixture` item reads its body from `fixtures/triage/<body>.md` and its ground truth (facts, expected claim ids) from the matching `.yml`. `bench triage --root bench` writes `triage/triage.json` (bodies and truth, ids sorted) and prints the dev scores.

The split is the scenario rule applied to the item id: dev when the first four bytes of `sha256(id)` mod 100 are under 60. `TriageBench.scoreDev` reads only dev items. `TriageBench.scoreTest` needs the `Unsealed` proof, so the test items are not scored before the unseal.

Scores run `Triage.run` on each body with the full rule catalog:

- Fact precision and recall: a fact counts when key, value and side all match the label. Wilson intervals.
- Brier: the fact confidence against whether the fact is labelled, with a 95 percent interval from 2,000 bootstrap draws over items (seed 20261015).
- Claim precision and recall: claim ids raised against the labelled ids. The claim check is experimental and its numbers are reported as measured.

Only fixture bodies are used. The fixtures were written while the extractor and the claim cues were tuned against them, so these scores bound the engine from above and say nothing about unseen issues. A corpus-derived item would use another `source` and carry its own body; the generator refuses any source but `fixture` until the corpus is decided.

## Upgrade Check

`upgrade/` is a third category, scored on its own and never pooled with the scenarios or the triage items. Its items come from the scenarios whose template id starts with `migration-`; no file is maintained by hand. Each scenario with a cause gives two items:

- `break`: the passing arm's committed capsule (`data/capsules/<id>.green.json`) and a `--to` target that sets the cause path to the failing arm's value. The truth is the measured red arm, which failed.
- `control`: the failing arm's capsule and a target set to the passing value. The green arm passed every trial, so nothing breaks.

The direction comes from `cause.direction` per template. The four templates with dev instances (`migration-jdk-list-getfirst`, `-node-array-fromasync`, `-php-json-validate`, `-python-copy`) fail on the older side, so their `break` items are downgrades from the passing capsule. The templates added later fail on the newer side for removals (Python 3.12 and 3.13, PHP 8.0, Node 23, Ruby 3.4, Gradle 9) and on the older side for `drupal-php-floor` and `spring-boot-3-class-version`; their direction is read from `cause.direction`, not assumed.

`bench upgrade --root bench` runs `UpgradeCheck` on every dev item with the full rule catalog, writes `upgrade/upgrade.json` (item, target and the rule ids found per group) and prints the dev scores. `UpgradeBench.runTest` needs the `Unsealed` proof, as `TriageBench.scoreTest` does. Test scenarios have no capsule until they run, so only dev items exist before the unseal.

Scores are per group (`will-break`, `version-boundary`, `may-break`, and `any` of the three) and per stratum, with Wilson intervals:

- A finding is confirmed when one of its rule's symptom texts contains the scenario's failure signature. Precision is confirmed findings over all findings reported in the group, on `break` and `control` items. Recall is the share of `break` items with a confirmed finding. Locked-package findings carry no symptom text and count as reported, never as confirmed.
- A scenario is rule-matched when some rule in the catalog has a symptom that contains its signature, whatever the check reported, and unmatched otherwise. Unmatched items cap recall at zero by construction.

The four dev scenarios and the rules for their APIs were written the same night from the same list of causes, so the rule-matched dev numbers are circular and bound the engine from above. The authorship split (template authors do not read `rules/`, rule authors do not read `scenarios/`) covers the templates added afterwards, which are all test items. It is an instruction to agents and people, not something the build checks.

A capsule from `drift capture` holds no `project.*` facts, and a rule that needs one (`project.python.calls.copy.replace`, for example) does not match when the fact is absent. The committed capsules therefore never confirm an API rule, whatever the engine does with a project scan. The test `theApiRuleIsWillBreakOnceTheCaptureHoldsTheProjectFact` adds the fact by hand to show the rule fires then.

## Calibration

`calibrate` ranks the capsule pair of every dev scenario with the real `Ranker`, compares the order and the probabilities with the injected cause, and writes two generated files under `data/calibration/`. `Lab` refuses a test id, so no fit or evaluation path can reach a sealed scenario. The probed lab leaves out the dev scenarios in `Lab.UNPROBED`, which have no probed capture because their programs read a file the harness mounts, and applies the same exclusion to the `original` input so every section scores the same ids.

`evaluation.json` holds, for each model, in-sample metrics and 5-fold cross-validated metrics (fold = first 4 bytes of `sha256("fold:" + id)` mod 5): top-1, top-3, MRR, Wilson intervals, Brier score, a reliability table, tier counts, false confidence, bundle honesty, decoys, controls and manual scenarios. The baselines are a random order (closed-form expectation), the raw diff in alphabetical order, the raw diff in the order `drift diff` prints it (dimension, then path), the changed attributes by dimension prior alone, the ranker's candidates by matched rule weight alone, and the hand-set ranker. `fit.json` holds the fitted table, the provenance (seed, scenario list hash, dev ids hash, method) and the selection: models are tried simplest first and one replaces the best so far only when its out-of-fold Brier is at least 2 percent lower and its out-of-fold MRR is not lower.

`evaluation.json` also holds an `analysis` section over the probed pairs, from the committed data only:

- `bootstrap`: 10,000 resamples of whole templates with replacement (seed 20261006), percentile intervals (2.5 to 97.5) for top-1, top-3 and MRR of the hand-set order and of each baseline, and the paired difference from the hand-set order on the same draws. Scenarios without a cause do not enter. Templates are the unit because siblings of one template share a cause and a capsule shape.
- `power`: the sample size each claim needs, from the current counts (formulas in `Analysis.kt`). Some inputs are planning values and the row says so.
- `bundle_honesty`: bundle-class scenarios scored against the declared bundle members plus the cause: how often the ranked bundle holds the cause, its mean size, and the share of its members that are declared (precision) and of declared members it holds (recall).
- `false_confirmed`: the bound on false CONFIRMED verdicts per CONFIRMED verdict (59) and per run (180), with the counts needed for 1 percent. The Lab counts are recorded in the technical report; the certificates are not in the repository.

`evaluation.json` has three sections: `probed` (the baseline captures of `solve`, with probes, the input of the fit), `probes_removed` (the same pairs without probes, so the effect of probes is a paired comparison) and `original` (the capsules the scenarios were validated with, no probes). The probed pairs come from the reproduce containers, so a cause a container cannot set (kernel, CPU model, browser) is absent from them; the `original` section keeps those. `reversed` swaps green and red on the probed pairs to exercise the rule tiers, because the dev scenarios fail on the older side and the catalog rules describe upgrades.

A probe supports a candidate only when it reads the candidate's attribute path (`ProbeLinks` in `core`). `by_evidence` in each model block groups the rankings by the evidence they carry: `attribute_only`, `with_probe`, `with_dimension_probe` (a probe differs in the candidate's dimension but does not read its path) and `with_rule`. On the dev pairs the attribute link and the earlier dimension link give identical rankings, tiers and rates, so the dimension-level group is small (3 rankings) and no candidate is demoted by it. The dev scenarios inject decoys that are real differences, so a probe that reads a decoy's path agrees with it: 10 of the 19 `plausible` candidates are wrong.

Only rankings whose candidates all rest on an attribute change get a printed probability, so the Brier score used for selection is taken over those rankings (`covered`) and the none weight is fit on them. `probe_sweep` scores the readout at several probe ratios on the rankings that carry a probe, next to saying one in n.

No dev scenario has a rule match or a history, so rule and spectrum weights are untested. The scenarios are synthetic: the share whose cause is invisible, or that have no cause, is a property of this set and not of real failures.
