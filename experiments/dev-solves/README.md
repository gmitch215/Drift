# Dev Solves

Question: when `drift solve` returns a verdict on a dev scenario, how often does it name the injected cause?

The experiment scores the certificates of 115 dev scenarios, one `drift solve` run each, against the labels in `bench/data/scenarios.json`. A CONFIRMED verdict is correct when its minimal set is exactly the injected cause. A control is correct when the verdict names no cause (NEEDS or STUCK). The full outcome list and the intervals are described under Solve Scoring in `bench/README.md`.

A pass is `bench/data/solves/dev.json` regenerated byte for byte from `certificates/`, `bench/data/solves/dev-after.json` regenerated byte for byte from `certificates/` with `certificates-after/` replacing the cases it holds, `bench/data/solves/dev-limits.json` regenerated byte for byte from `certificates-limits/` alone, `bench/data/solves/dev-x1-a.json` regenerated byte for byte from `certificates-x1/` alone, and `bench/data/solves/dev-p8.json` regenerated byte for byte from `certificates-p8/` alone. The score itself is a measurement, and `results/dev-solves/latest.md` records both runs.

## Inputs

| path | content |
| --- | --- |
| `certificates/<id>/certificate.json` | the certificate of the final solve of each dev scenario that `drift solve` can run: 66 from the re-solve with the fixed Lab and 49 older scenarios |
| `certificates-after/<id>/certificate.json` | the certificates of the scenarios solved again after the Lab fixes (`reproduce` base image choice, alpine point release tags, XDG variables); each replaces the case of the same id in `certificates/` |
| `certificates-limits/<id>/certificate.json` | the eight `limits-*` scenarios solved once after capture began to record `limits.*`; they are scored on their own and are not part of `dev.json` or `dev-after.json` |
| `certificates-x1/<id>/certificate.json` | 38 scenarios solved once after capture began to record hosts, name service switch, interface and CPU affinity facts: the eleven scenarios that changed state, all 10 controls and all 19 decoys; scored on their own |
| `certificates-p8/<id>/certificate.json` | 53 scenarios solved once after the member experiments and the NEEDS verdict: 15 bundle scenarios, 11 intermittent, 10 controls, the other scenarios that had ended STUCK, and the nine whose scenario defect was fixed (the four shell scenarios, the two version pins, the lockfile pin and the two checksum pins; their capsules were recorded again); scored on their own |
| `bench/data/scenarios.json`, `bench/data/split.json` | the labels and the dev split |
| `bench/data/calibration/evaluation.json` | the ranker and dimension-prior ranks that the comparison block uses |

The four pin scenarios `build-checksum-pin-1/2` and `build-version-pin-1/2` have a case in `certificates-p8/` only; `network-hosts-stale-1/2` and `network-nsswitch-order-1` are in `certificates-x1/`. A test id in a case directory is refused.

## Running

```sh
experiments/dev-solves/run.sh --check
experiments/dev-solves/run.sh
experiments/dev-solves/run.sh --after
experiments/dev-solves/run.sh --limits
experiments/dev-solves/run.sh --x1
experiments/dev-solves/run.sh --p8
experiments/dev-solves/run.sh --solved DIR[,DIR...] --out DIR
```

`--after` scores `certificates/` with the cases of `certificates-after/` swapped in and compares with `dev-after.json`. `--limits` scores `certificates-limits/` and compares with `dev-limits.json`. `--x1` scores `certificates-x1/` and compares with `dev-x1-a.json`. `--p8` scores `certificates-p8/` and compares with `dev-p8.json`. `--check` confirms that every case directory holds a certificate and that the committed `dev.json` counts the same cases (with `--after`, that each replacement matches a case and `dev-after.json` counts the same). It needs no Gradle and no network. A run copies the label files into a scratch bench directory under `--out`, runs `bench solves` there through Gradle, writes `report.txt`, and compares the result with `bench/data/solves/dev.json`. It exits 1 when they differ. The run needs a JDK and the Gradle wrapper, and no Docker. It takes under two minutes once Gradle has built `bench`.

`OUT_DIR` sets the default output directory, `SOLVED` the default case directories, and `GRADLE` the launcher and its flags. Raw output goes under `experiments/results/dev-solves/runs/`, which is ignored.

## Regenerating the Solves

A new set of certificates is a new measurement. Its `dev.json` can differ from the committed one, so keep it under `runs/` and record it in `latest.md` when it is accepted. The flow is the one in `bench/README.md`:

```sh
./gradlew :bench:jvmRun --args="prepare --root $PWD/bench --out DIR"
./gradlew :cli:linkReleaseExecutableLinuxX64
sh DIR/prepull.sh DIR --pull
DRIFT=cli/build/bin/linuxX64/releaseExecutable/drift.kexe sh DIR/run-solve.sh DIR --jobs 2
./gradlew :bench:jvmRun --args="solves --root $PWD/bench --solved DIR/../solved"
```

`prepare` writes one directory per dev scenario with `solve.sh`. `run-solve.sh` solves them one or `--jobs` at a time into `DIR/../solved/<id>`, needs Docker and the arm images, and stops below 25 GB free. Capsules recorded on aarch64 need an arm64 Linux executable, and on an x86-64 host the arm images run under qemu-user-static. The last command overwrites `bench/data/solves/dev.json`, so point `--root` at a copy of `bench/` to keep the committed file.

The committed certificates come from solves on paisley-park (Docker, qemu for the aarch64 capsules). The certificate of `env-pip-cache-dir-1` records an executor failure from a Docker image that was removed mid-run; its re-solve ended STUCK with 0 of 30 trials failing, and that certificate is not kept.

The second run solved 21 of the 55 stuck scenarios again with binaries built from the fixed tree, plus `runtime-rust-newer-std-1` and `runtime-go-loopvar-1` to check that the environment-variable change leaves their verdicts alone. It used the same flow with `SOLVED` pointing at a new directory and `run-solve.sh --jobs 2`; the `images` check covers the scenario's own base images, so the arm images that the fixes choose (`alpine:3.22.6`, `gcc:15.3`, `ruby:3.4.11-slim-trixie` and others) were pulled by hand first.
